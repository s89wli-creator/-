# 00 — تحليل المشروع والمخاطر والنواقص

> المنتج: **راكان — AI Sales Employee**
> المرحلة: Discovery (المرحلة الأولى)
> الحالة: مسودة للاعتماد
> التاريخ: 2026-11-09

---

## 1. خلاصة التحليل

راكان منتج SaaS متعدد المستأجرين (Multi-Tenant) يقدم "موظف مبيعات ذكي" للشركات السعودية التي تبيع B2B وتعتمد على المندوبين الميدانيين. القيمة الأساسية ليست في CRM بحد ذاته، بل في **الطبقة الذكية فوق CRM**:

1. **Sales Brain**: معرفة الشركة البيعية المنظمة (منتجات، ICP، اعتراضات، سياسات، ممنوعات).
2. **وكلاء متخصصون** يعملون عبر أدوات محددة الصلاحيات.
3. **تجربة ميدانية** للمندوب (PWA، Offline، تسجيل الزيارة خلال دقائق).
4. **حوكمة**: موافقات بشرية، سجل تدقيق، مصادر وثقة لكل استنتاج، حدود استهلاك.

الميزة التنافسية المتوقعة في السوق السعودي: Arabic-first حقيقي، فهم الزيارات الميدانية (وليس فقط البريد والاتصالات كما في أدوات المبيعات الغربية)، والامتثال لنظام حماية البيانات الشخصية (PDPL).

## 4. تدفقات العمل الأساسية (Flows)

### 4.1 دورة البيع الكاملة

```
[Import / Prospecting] → Lead (stage: new)
   → Lead Intelligence: score + reasons + sources → (stage: analyzed)
   → Manager/Rule: qualified? → (stage: qualified) → assign to Rep
   → Rep: contact → (stage: contacted) → schedule visit → (visit_scheduled)
   → Field Sales Agent: Pre-Visit Brief
   → Rep: check-in → notes/voice → check-out → (visit_done)
   → Meeting Intelligence: summary, needs, objections, interest, next step
   → Follow-up Agent: draft message + follow-up task  ──► Approval Queue ──► Send
   → Opportunity: proposal → negotiation → won / lost / postponed
   → Sales Coach + Reports
```

### 4.2 تدفق الإجراء الحساس (Human-in-the-loop)

```
Agent proposes action (tool call with risk = EXTERNAL or IRREVERSIBLE)
  → Tool Gateway يرفض التنفيذ المباشر
  → ينشئ ApprovalRequest(payload, reason, sources, confidence)
  → إشعار للمدير
  → Approve  → التنفيذ عبر نفس الأداة بتوقيع الموافقة + Audit Log
  → Reject   → تسجيل السبب، إعادة للوكيل/المندوب
  → Expire   → يلغى تلقائياً بعد مدة محددة
```

### 4.3 تدفق الزيارة دون إنترنت

```
Rep opens PWA (cached brief) → check-in (local timestamp + optional GPS)
  → notes / voice (IndexedDB, encrypted at rest on device where possible)
  → check-out → queued in Outbox (idempotency key per record)
  → Connectivity restored → Background Sync → API (dedupe by client_id)
  → Server ack → Meeting Intelligence job queued
```

## 5. المخاطر

| # | الخطر | الأثر | الاحتمال | المعالجة |
|---|---|---|---|---|
| R1 | **تسرب بيانات بين الشركات** (عبر استعلام، Cache، Vector search، أو سياق LLM) | حرج | متوسط | `tenant_id` في كل جدول + **PostgreSQL Row-Level Security** كطبقة دفاع ثانية + مفاتيح Cache تبدأ بـ tenant + فلترة إلزامية في Vector search + اختبارات عزل آلية في CI |
| R2 | **هلوسة الذكاء الاصطناعي** (اختلاق أرقام، أسماء مسؤولين، ميزات) | عالي | عالي | Structured Outputs + إلزام حقل `sources[]` + رفض المخرجات بدون مصدر للحقائق + فصل "قال العميل" عن "استنتاج AI" + Sales Brain كمصدر وحيد لادعاءات المنتج |
| R3 | **نظام حماية البيانات الشخصية (PDPL)** ونقل البيانات خارج المملكة لمزودي LLM | حرج | عالي | استضافة البيانات داخل المملكة، تقليل البيانات الشخصية المرسلة للـLLM (PII minimization/redaction)، اتفاقيات معالجة البيانات، سجل المعالجة، تقييم أثر قبل الإطلاق، مراجعة قانونية متخصصة **(قرار يحتاج مستشار قانوني)** |
| R4 | **تسجيل الاجتماعات صوتياً** بدون موافقة | قانوني/سمعة | متوسط | خطوة موافقة إلزامية في الواجهة قبل التسجيل + تسجيل نص الموافقة ووقتها + إمكانية إيقاف الميزة على مستوى الشركة |
| R5 | **مصادر بيانات Prospecting** محدودة أو غير مصرح بها (Scraping مخالف للشروط) | عالي | عالي | الاعتماد على مصادر مرخصة/APIs رسمية (Google Places، مزودي بيانات تجارية)، تسجيل المصدر والتاريخ، عدم جمع بيانات شخصية، Prospecting في V1 يقتصر على بيانات الشركات العامة |
| R6 | **ضعف دقة Speech-to-Text للهجات السعودية** وضوضاء الميدان | متوسط | عالي | طبقة STT قابلة للتبديل، اختبار عدة مزودين على عينات حقيقية في Pilot، السماح للمندوب بتصحيح النص، الملاحظات النصية بديل دائم |
| R7 | **تكلفة AI غير منضبطة** | مالي | متوسط | Budget لكل شركة/شهر + Hard limit + تقدير التكلفة قبل التنفيذ + Model routing (نموذج أرخص للمهام البسيطة) + Caching |
| R8 | **Prompt Injection** عبر مستندات Sales Brain أو رسائل العملاء أو صفحات الويب | عالي | متوسط | معاملة كل المحتوى الخارجي كبيانات غير موثوقة، فصله في السياق، الأدوات الحساسة تتطلب موافقة دائماً بغض النظر عن مخرجات النموذج، Allow-list للأدوات لكل وكيل |
| R9 | **WhatsApp Business**: قيود القوالب والموافقة المسبقة (Opt-in) وتكلفة المحادثات | متوسط | عالي | V1: إعداد الرسائل والاعتماد ثم الإرسال اليدوي/Click-to-chat، التكامل الرسمي في مرحلة لاحقة مع إدارة Opt-in |
| R10 | **اعتماد المندوبين** (رفض الاستخدام أو التسجيل الناقص) | عالي | متوسط | تسجيل زيارة ≤ 3 دقائق، إدخال صوتي، فائدة مباشرة للمندوب (بطاقة الزيارة، رسائل جاهزة) |
| R11 | **التخصص الزائد في قطاع النقل** بسبب Pilot انجزني | استراتيجي | متوسط | كل خصائص انجزني تكون **إعدادات وبيانات** (Custom fields، Segments، Pipelines، Sales Brain)، لا كود خاص بانجزني |
| R12 | **إثبات الزيارة** والاعتماد على GPS وحده | متوسط | متوسط | GPS كمؤشر فقط + Check-in/out + ملاحظات + مرفقات + تأكيد لاحق من العميل اختيارياً، دون الاعتماد عليه في تقييم الموظف |
| R13 | **تقييم الموظفين ببيانات ناقصة** (Sales Coach) | قانوني/ثقافي | متوسط | حد أدنى من البيانات قبل إصدار أي تقييم + عرض درجة الثقة + التوصيات تدريبية وليست عقابية + لا يظهر التقييم للمندوبين الآخرين |
| R14 | **الاعتماد على مزود AI واحد** | متوسط | — | AI Provider Abstraction + Capability registry (دعم العربية/الأدوات/Structured output لكل نموذج) |

## 6. النواقص والأسئلة المفتوحة في المتطلبات

نقاط يجب حسمها مع صاحب المشروع (لا تمنع البدء في Foundation):

| # | السؤال | الافتراض المؤقت المعتمد في التصميم |
|---|---|---|
| Q1 | هل توجد قاعدة عملاء انجزني فعلية؟ ما صيغتها وما مصدرها وهل يحق استخدامها (موافقات)؟ | سيتم استيرادها كملف Excel بعد تأكيد الصلاحية؛ لا بيانات وهمية تقدم كحقيقية |
| Q2 | معلومات انجزني الرسمية (الخدمات، الأسعار، الشروط، السياسات) | تُجمع من الشركة مباشرة في نموذج Sales Brain؛ كل حقل غير مؤكد يبقى فارغاً بحالة "بانتظار التأكيد" |
| Q3 | مزود الدفع للاشتراكات (Moyasar / HyperPay / Tap / Stripe) | طبقة Billing مجردة؛ يُقترح **Moyasar أو Tap** لدعم مدى و Apple Pay والفوترة بالريال، والقرار عند المرحلة السادسة |
| Q4 | الفوترة الإلكترونية (ZATCA – فاتورة) لفواتير الاشتراك | مطلوبة عند البيع التجاري؛ تؤجل لـPhase 6 وتُنفذ عبر مزود معتمد |
| Q5 | موقع الاستضافة (داخل المملكة) | يُقترح مزود سحابي بمنطقة داخل المملكة (انظر وثيقة التكاليف)؛ القرار قبل Pilot بالبيانات الحقيقية |
| Q6 | هل يُسمح بإرسال بيانات العملاء (أسماء شركات، ملاحظات زيارات) لمزودي LLM خارج المملكة؟ | الافتراض: **نعم لبيانات الشركات (غير شخصية)** مع إخفاء البيانات الشخصية (أسماء الأشخاص، الجوالات) قبل الإرسال، وتحتاج مراجعة قانونية |
| Q7 | اسم المنتج النهائي والعلامة: "راكان" | يُستخدم "راكان" اسماً للوكيل والمنتج في الواجهة |
| Q8 | عدد المندوبين في Pilot انجزني ومدته | الافتراض: 2–5 مندوبين، 6–8 أسابيع |
| Q9 | هل يحتاج المدير تطبيق جوال أصلي؟ | لا؛ PWA يكفي في V1 |

## 7. قرارات تقنية مقترحة على المواصفات الأصلية

جميع التقنيات المقترحة في البرومبت **معتمدة** (Next.js، NestJS، PostgreSQL، pgvector، Redis + BullMQ، Modular Monolith). الإضافات/التوضيحات:

| القرار | السبب | التكلفة | المخاطر |
|---|---|---|---|
| **Monorepo (pnpm + Turborepo)** | مشاركة الأنواع (Types) و Zod schemas بين الواجهة والخادم | لا شيء | تعقيد بسيط في الإعداد |
| **Drizzle ORM بدلاً من Prisma** | تحكم كامل في SQL و RLS و pgvector، وسهولة تنفيذ `SET LOCAL app.tenant_id` داخل المعاملة | لا شيء | فريق أقل خبرة بـDrizzle مقارنة بـPrisma |
| **PostgreSQL RLS** كطبقة عزل ثانية | عزل البيانات لا يعتمد على تذكر المطور إضافة `WHERE tenant_id` | أداء ضئيل | يتطلب انضباطاً في أدوار قاعدة البيانات (التطبيق لا يتصل كـsuperuser) |
| **Auth داخلي** (Sessions + Argon2id + Refresh rotation) بدلاً من مزود خارجي في V1 | التحكم بموقع البيانات، لا تكلفة لكل مستخدم، تكامل مباشر مع RBAC والمستأجرين | وقت تطوير ~1 أسبوع | يجب اتباع معايير OWASP بدقة؛ SSO للمؤسسات لاحقاً |
| **مخرجات AI عبر Zod schemas** | Structured outputs موحدة بين المزودين والتحقق قبل الحفظ | لا شيء | — |
| **Worker منفصل** (نفس الكود، عملية مستقلة) | تشغيل الوكلاء والمهام الثقيلة خارج مسار الطلبات | خادم إضافي صغير | — |

لا يوجد أي تغيير على نموذج العمل أو الأسعار أو الصلاحيات المطلوبة.
